# Rulith branch

This branch is upstream [llama.cpp](https://github.com/ggml-org/llama.cpp), merged in (most recently `19ab5a5` of 2026-10-22), plus the changes of [Rulith Inference](https://github.com/rulith-dev/rulith-inference): 159 files (119 modified, 40 added) that make Qwen3.8-Flash-Next fast on one AMD Strix Halo machine (Ryzen AI Max+ 395, Radeon 8060S / gfx1151) on Windows, built with HIP against TheRock ROCm 10.2. Up to 0.6.4 the base was `pwilkin/llama.cpp` at `f5daaa3`.

The recipe that rebuilds this tree from clean upstream (`bootstrap/bootstrap.py`, a script per area plus whole files, regenerated from the two commits by `tools/make_recipe.py` whenever upstream is merged), a replay that checks every file by hash, the manager, the desktop app, and the measurements live in the main repository:

https://github.com/rulith-dev/rulith-inference

What the delta does, in one line each (the reasons, change by change, in that repository's `patches/history/`):

- sparse-attention (QSA) block-key cache (a rebuild scores with the keys as the cache stores them, as every later graph does), decode-time gather, compact metadata, an image guard for M-RoPE cells
- mixed-sequence batches stay on the sparse path, so several conversations at depth share a step instead of falling back to dense attention over the whole pool
- with several slots in one pool, a batch's sparse-attention block list covers only its own conversations, so idle ones cost a decoding conversation nothing per step; a slot's state is read from the device one run of cell ranges at a time rather than one range at a time (a conversation decoded alongside others had stalled the server 6-10 s at every save)
- with several slots, every conversation keeps one run of the pool and a batch's graph views only the runs of its own conversations, so a conversation beside idle ones computes, and costs, what it does on a single slot - the MTP draft's dense attention included; a batch that does not fit has the pool laid out again on the device first (conversations kept in order, the same room after each one of the batch)
- compute buffers get a little headroom, so a graph a few MiB larger no longer frees and reallocates one: ROCm on Windows keeps a freed buffer's commit, and four long conversations ran the machine into its commit limit ("bad allocation")
- a slot named by id that holds nothing reads its conversation back from the prompt cache: its f_keep was 0/0, a NaN that skipped the cache, so a 173K-token conversation sent back to its emptied slot was processed again (186 s) instead of read back from the disk tier (7 s)
- a slot that fails part way through its turn loses its conversation, and a prompt batch starts only on a cache whose positions match its tokens: near the commit limit an exception had left a slot's tokens and memory apart, and the next request fed the recurrent state positions it had seen or skipped (GitHub issue #1); a leaving conversation also keeps a checkpoint every 32K tokens in the disk tier
- the disk tier and that check with a vision projector loaded: every prompt counts as a media prompt to server_tokens::get_tokens() then, which asserts, so version 3 aborted the server when the disk tier and image input were both on; it reads the text tokens, and the check skips only prompts that hold media
- a Q8_0 K/V cache: the sparse-attention prefill kernel reads packed f16 layouts, so the graph dequantizes a Q8_0 cache into them, and decode's gather and the block-key rebuild read Q8_0 rows; the indexer's keys stay f16, and V is not rotated for this architecture (the kernel's matrix-core sums move in the last bit with the V of keys weighted by zero, and a rotated V spread that into a restored conversation)
- several conversations at once draft less: `STRIX_SPEC_DRAFT_BY_SLOTS` caps a step's draft by how many slots generate (in this MoE every verified draft token reads ~10 more experts' weights, which conversations decoding together cannot share), and the MTP draft stops at that cap
- the drafts of one speculative step are the same length for every conversation (`STRIX_SPEC_EVEN_DRAFTS`): the hybrid memory runs a batch as ubatches with the same tokens for every sequence, so a verify of uneven drafts was two or three passes of the whole model in shapes the graph cache had not seen; and the sparse attention's block-membership product for several conversations has a kernel of its own instead of hipBLAS, which loaded a kernel from disk on first use of each shape (`STRIX_SMALL_K`)
- a verify step of several conversations (5-16 tokens) keeps the MoE router (an F32 [2560 x 512], 9-32 columns) and the routed experts past the vector kernel's limit on the vector kernel, in column and token chunks (`STRIX_F32_VEC_CHUNK_MAX`, `STRIX_MOE_VEC_CHUNK`): they fell to a four-workgroup MMB tile and to MMQ tiles one or two tokens full, 16 ms of a nine-token step
- and three more of its products off few-workgroup kernels: the GDN conv input's concat of 2-31 transposed tokens on the tiled transpose (`STRIX_CONCAT_T_MIN`), the indexer's BF16 k projection at 9-32 columns on the vector kernel in column chunks (`STRIX_BF16_VEC_CHUNK_MAX`), quantized weights of at most 1024 rows at 9-32 columns on the vector kernel in 8-column chunks (`STRIX_Q_VEC_CHUNK_MAX`, `STRIX_Q_VEC_CHUNK_ROWS`): a nine-token step 104-106 -> 99-100 ms
- the sparse-attention indexer's BF16 projections on the MMB kernel from 9 columns (`STRIX_MMB_BF16_MIN_T`), and Q6_K on MMQ at every width on RDNA 3.5 (`STRIX_MMQ_Q6K_ANY`): a chat turn's 17-511-token batch and the draft head's first prompt batch went to hipBLAS, which loaded a kernel from disk the first time (0.2-0.4 s)
- a freed K/V cell is zeroed, so the free cells a batch's sparse attention reads past (weighted by zero, but moving the matrix cores' sums in the last bit) no longer carry an earlier conversation's or a rejected draft's rows
- the MTP drafter's carried target row keeps its position and goes with checkpoints, the prompt cache's entries and the disk tier's restore point: after a rewind the draft had paired its first token with a stale row
- MTP speculative decoding: the draft context's ubatch capped separately, the draft's own sparse-attention prefill, shape-keyed HIP graphs
- per-layer-embedding table read with unbuffered, overlapped direct I/O instead of the pager (`--load-mode none --lazy-mode on-direct`), so a 93.7 GB model runs in a 96 GB carve with the table on disk; the server gathers the next prompt batch's rows while the current one computes (`llama_strix_prefetch`)
- a disk tier under the server's prompt cache, kept per model: a conversation's attention rows by position (`llama_strix_kv_*`), in runs of 4096 positions written once each as they are computed, named by their hash; its recurrent state only when it leaves memory (evicted, or on `POST /strix/persist` before a stop); a restore streams the runs back and puts back the latest checkpoint they reach, bitwise what the resident conversation computes. One background writer, reads and writes straight from the device rather than through the page cache, and the store keeps only the format the build writes
- a few fused HIP kernels (chain fusion, getrows cast, an IQ3_S vec-dot, RDNA 3.5 row tiles for mmvq, a vector path for few-row matmuls past 8 columns), and the base's hyper-connection gate and PLE conv fusions extended to Unsloth's weight types (Q8_0, F32) with the unfused path's numerics
- the routed IQ3_S expert gate/up + SwiGLU, prefill's largest kernel, rebuilt for gfx1151, where the VALU and the WMMA unit never overlap: its dequantization spread over the block and cut to fewer instructions per weight, its loads kept off the critical path - 1.8x, bitwise the same output
- the rest of a prefill batch: the hyper-connection inject computed inside the combine-norm kernel while its input is in registers; TOP_K as a radix select over a row held in registers (the same selected set); the QSA key and value packs written from the cache in one pass instead of two full copies; the attention gate's copy and sigmoid, and the indexer's strip score, one kernel each; a gated delta net prefill kernel with 16 state rows a lane group and the state scaled by its decay; narrow F32 weights on their own kernels, and F32 GEMMs from 9 columns on WMMA instead of hipBLAS, which loads each of its kernels from disk on first use; BF16 activation rows padded off the memory channels' 4 KB stride. Not bitwise to the previous release (the same accuracy); bitwise with `STRIX_HC_INJECT_FUSE=0 STRIX_GDN_R16=0 STRIX_SKINNY_F32=0 STRIX_MMB_F32_MIN_T=512`
- the gated delta net reads its recurrent states in place when every sequence of a batch reads a row of its own cell (its newest state, or a rollback snapshot after rejected drafts) instead of gathering them into scratch; with several conversations decoding, its output projection is one product rather than one per sequence
- the per-layer-embedding rows read with `FILE_FLAG_NO_BUFFERING`, 16 requests in flight on each of 16 workers, with no buffered handle or mapping of the file left open, and a RAM cache of the rows read (`STRIX_PLE_CACHE_MB`, default 400)
- smaller: a bitonic sort for the QSA3 selection rows, conv-state tails copied without a cont

Measured on the target machine: prefill 1187 tok/s over 95.6K tokens of real text, decode 34.9 tok/s at 85K tokens of context (MTP acceptance 68%). Numbers, method and the ways we measured it wrong first: `docs/results.md` and `docs/measuring.md` in the main repository.
