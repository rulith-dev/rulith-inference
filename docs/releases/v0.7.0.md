Rulith Inference 0.7.0 brings long conversations back from the SSD cache whole ([#30](https://github.com/rulith-dev/rulith-inference/issues/30)), keeps conversations with images there too ([#31](https://github.com/rulith-dev/rulith-inference/issues/31)), restarts a model load that stops making progress ([#29](https://github.com/rulith-dev/rulith-inference/issues/29)) and no longer runs a cancelled request later ([#28](https://github.com/rulith-dev/rulith-inference/issues/28)).

**Conversations come back from the SSD cache whole (#30)**
- A conversation that had left its slot was matched against the SSD cache by its raw tokens. The model's own answers are stored as the tokens it sampled, while the next request carries the same text tokenized again; the two can differ in places, and the match stopped at the first such place. In the report, 8,192 of a 125,529-token conversation came back and 117,452 tokens were read again (85 s).
- The SSD and RAM tiers now match a stored conversation the way a resident one already was matched since 0.6.0: the model's own tokens count as the text they spell. Checkpoints qualify only up to where that match holds, and a conversation that returns right after it was saved waits for its own write instead of missing it.
- Each lookup now logs every candidate it considered: its common prefix, how far it can be restored, the checkpoint it would use and why it lost.
- Thanks to @depechetoi for the careful report.

**Conversations with images stay on the SSD cache (#31)**
- The SSD cache did not store conversations with images, and a state larger than the RAM cache (4.6 GB against 1 GB in the report) was simply dropped: resuming read 117,975 tokens again.
- Such conversations are now saved and restored too. An image matches only the same image at the same place; a conversation saved with another image projection setting comes back up to its first image.
- Thanks to @depechetoi for the report.

**A model load that stops making progress is restarted (#29)**
- On one machine the default loader (`--load-mode none --lazy-mode on-direct`) waited forever while loading weights, with nothing in the log; the mmap loader worked.
- The engine now writes a progress line every 10 seconds while it reads weights. If those lines stop for four minutes, the app stops the load and starts it again with `--load-mode mmap --lazy-mode on`, and that model keeps the mmap loader on this PC.
- Thanks to @abacist2012 for the detailed report.

**A cancelled request no longer runs later for nobody (#28)**
- A request cancelled while it waited for a free slot could be taken back into the queue a moment after the cancel had looked for it, and then ran once a slot came free, with nobody listening. Its slot showed as busy for the whole answer.
- The server now also writes a warning when a slot stays busy for 10 seconds without doing anything, naming its state. `next_token.n_decoded` in `/slots` counts the tokens of the slot it is listed under; an idle slot shows 0 and `n_remain` -1.
- Thanks to @biolau for the report.

**8-bit keys of Qwen3.8-Flash-Next no longer rotated**
- Qwen3.8-Flash-Next's keys were rotated with a Hadamard transform before 8-bit quantization. For this model it made long-range copying worse in the engine's own test, where four passages from about 200K tokens back are copied one after another: decode loss 0.788 with the rotation, 0.150 without. The rotation is off for this model now. A single 178-word paragraph placed 200K tokens back is copied word for word by both 0.6.11 and 0.7.0; the difference shows in the harder test.
- The selection of top-k candidates now writes them in a fixed order, so repeated runs of one request give the same values.

**For people who build the engine themselves**
- The engine source is `rulith-dev/llama.cpp`, branch `rulith`, commit `6ae1f73ee`. The patch set replays byte for byte; `patches/MANIFEST.md` records the changes and their measurements.
